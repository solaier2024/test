# Penalty Shootout — 点球大赛即时赢游戏

墨西哥 / 美国市场的足球点球大战即时赢（instant-win）游戏。

本分支 `cursor/penalty-shootout-7c4b` 承载该项目。

## 为什么是点球大赛

市场调研的结论是足球为首发品类：墨西哥第一运动（Mitofsky 2025，64% 爱好者），美国足球偏好率在 2026 世界杯后创 Gallup 历史新高（9%）。Evoplay 的数据显示点球题材在赛事结束后活跃度反而达到赛前的 6.5 倍，说明它不依附单一赛历。

品类已有 7 款在位产品（Evoplay 5 款、InOut 2 款）。初步调研显示它们以"连续命中次数"为核心而没有比分概念，本项目的差异化方向是比分驱动的情境决策、门将记忆与诱导、赛前阵容构筑、Liga MX 语境。

**这些差异化结论目前按待验证假设处理** —— 竞品 demo 实测（backlog `X-3`）完成前，不对外声称为竞品空白。

## 承重墙：现金价值的鞅条件

**深度不等于"技术好的玩家赢更多钱"。** 玩家掌控的是波动形态与会话节奏，不是期望值。

这是**产品设计目标**，不是监管要求。理由是 RTP 需可证明可认证：若策略间 EV 不同，最优策略的 EV 就定义了实际 RTP，其余策略成为陷阱。

> 注：墨西哥实施条例第 85 条涉及线上/电子接受投注的内控、记录与事前审批，**未规定每种玩家策略的 EV 必须相同**。监管立论与数学目标分开陈述。

正确的条件是现金价值 `C(s)` 的鞅条件，对**每个可达决策状态与每个合法继续动作**成立：

```text
C(s) = Σ P(s' | s, a, 可见信息) × C(s')      终局：C(s) = G(s)      初始：C(s₀) = W × r
```

**直接推论：`C` 必须能下降。** 否则"继续"的期望恒大于当前值，收钱永远是劣选，形成可被套利的无损增值区间。所以射门失败与对手进球都要降低当前可兑现金额。

> 仅平衡"命中率 × 倍率步进"**不能**替代该条件 —— 它只平衡了单次成功那一步，未纳入失败分支、终局、奖金与收钱权的价值。这是本项目 v1 方案的核心错误。

验证方式是**完整状态求解**而非列举策略的蒙特卡洛：

```text
Vmax(s) = max { C(s), max_a Σ P(s'|s,a) Vmax(s') }
Vmin(s) = min { C(s), min_a Σ P(s'|s,a) Vmin(s') }
```

鞅条件精确成立时 `Vmax(s₀) = Vmin(s₀) = W × r`。蒙特卡洛降级为回归与分布检查，须报告样本量、方差与置信区间。

无损区间检查与鞅条件回归进 CI 做门禁。实现时不要为了"手感"破坏这条原则。

## 技术架构

```
┌─ 表现层  Pixi + 视频播放器 + GSAP          零游戏逻辑，可整层替换
├─ 游戏外壳  轮次状态机 / 攻防阶段机 / UI 状态 / 资产调度
├─ OutcomeProvider（接口）  ←──── 服务端接入的唯一切换缝
│    ├─ LocalProvider   阶段一：本地 seed + 本地 PRF
│    └─ RemoteProvider  阶段四：服务端 seed + commit/reveal
└─ shootout-math（纯 TS，零依赖，Node 可运行，全单测 + 可模拟）
```

技术选型沿用对参考平台的实测结论：**PixiJS + GSAP + Rolldown/Vite**，**视频基座**（每种结果一条 mp4，Pixi 只负责 UI 与叠加层）。不需要骨骼动画。

### 服务端后期接入，且不返工

所有随机性由 `PRF(seed, 轮次, 阶段, 决策路径)` 导出。玩家的选择决定读取哪条随机分支，但影响不了分支内的数值；终局揭示 seed 即可完整重放。

阶段一本地生成 seed、使用完全相同的 PRF。接入服务端时只需把 seed 生成与承诺移到服务端、加上揭示校验 —— `shootout-math` 与表现层零改动。

赛前阵容顺序必须纳入决策路径的哈希输入，否则玩家可在看到结果后反悔重排。

### 视频资产规格（参考平台 ffprobe 实测）

| 项 | 值 |
|---|---|
| 编码 | H.264，**无音轨**（音频走独立 mp3 分层） |
| 结果片（横） | 1280×720 @24fps，2.5–5s |
| 背景循环 | 1280×720 @30fps，8s，218 kbps |
| 兜底 | 每条 mp4 配首帧 poster（webp/png） |
| 加载 | `media-manifest.json` 驱动按优先级渐进加载 |

**竖屏方案待选定**：参考平台的 720×540 是 4:3，适合作为**竖屏 UI 内的视频窗口**，不是竖向全屏。若要真竖向全屏需另定长宽比、机位与裁切方式（参考平台另有 720×2560 全高侧栏即为此类用途）。片单冻结前必须选定。

**主片数量 16 条是预算目标，不是已冻结的结论。** 按结果类别收敛而非区域组合展开（组合展开会达 84 条，成本不可接受），但**必须先用样片验证"固定片段能否覆盖任意所选方向与门将扑向"**，通过后再冻结片单。方向差异通过镜头机位 + Pixi 球轨迹特效表达。

## 实施阶段

| 阶段 | 内容 | 出口条件 | 美术 |
|---|---|---|---|
| **S0** | 结算灰盒：基础动作、比分、提前终局、限定骤死、收钱与现金价值 | 状态与终局表完整；求解范围明确；**无无损增值区间** | 0 |
| **S1** | 核心深度：对手原型、赛前倾向、有限门将记忆、关键球提示、战报 | 玩家能读懂并形成计划；新增状态通过数学验证 | 0 |
| S2 | 构筑联动：球员特质、压力等级、一次教练调整 | 构筑与调整有可见后果；自适应策略验证通过 | 0 |
| S3 | 表现验证：占位片、球轨迹、横竖屏、弱网降级 | 球路与扑救和结果一致；节奏实测通过 | 占位 |
| S4 | 快速模式：明确自动防守策略 | 模式目标 RTP 验证通过 | — |
| S5 | 资产与扩展：正式片单、本地化、成长、杯赛 | 前面规则与数据稳定；每项单独验收 | 正式 |

**首版 = S0 + S1。** 先证明核心选择有趣，再增加构筑联动。正式资产批量制作安排在 S3 覆盖验证之后 —— 数学与表现都未锁定时做资产返工风险高。

首版的操作面是**刻意缩减**的（3 方向 × 2 射法 = 6 种进攻组合，防守 3 方向；压力、阵容、快速模式后置）。这不只是认知负担考虑 —— **有限状态是完整求解可行的前提**，范围控制与可证明性是同一件事。

建议起手：backlog 的 `S0-1` → `S0-2` → `S0-3` → `S0-4`（无前置依赖）。
